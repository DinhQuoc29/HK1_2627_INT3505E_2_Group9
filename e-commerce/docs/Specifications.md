# Marketplace software specifications

These proposed specifications define software behavior and acceptance checks for the [requirements](Requirements.md). Each row links a requirement to the [risks](Risks.md) its checks address. The requirement records the applicable [assumptions](Assumptions.md) and [use cases](Use_Cases.md). The checks below describe expected results for implementation.

## V1 — First release

### Accounts and catalog

| SPEC | Requirement and risks | Software behavior | Acceptance check |
| --- | --- | --- | --- |
| SPEC-01 | REQ-01 · RSK-01 | Register a buyer under a unique email address and store a salted password hash. Issue a session after verifying credentials. For Google sign-in, verify the provider identity and resolve it to its linked marketplace account. Allow a signed-in buyer to link their verified Google identity. A provider failure leaves the account intact and offers a retry. | Register and return by password, link Google, then return by Google and find the same account and orders. Reject an incorrect password. Simulate Google being unavailable and verify that no session or duplicate account is created. |
| SPEC-02 | REQ-02 · RSK-02 | On logout, invalidate the current session on the server and clear its client credential. Check session validity on protected requests. | After each role logs out, repeat a previously successful protected request with the ended session. Access is denied. |
| SPEC-03 | REQ-03 · RSK-03 | Derive the acting user from the session. Scope cart and buyer-order operations to that user, seller operations to assigned shops, and administrative operations to admin permission. Apply the checks to reads and writes. | With two buyers and two shops, verify that each can act on its own records. Cross-account reads, cross-shop edits, and non-admin category changes are denied and leave records unchanged. |
| SPEC-04 | REQ-04 · RSK-04 | Give each category a stable identifier and an optional parent. Use the same hierarchy for seller selection and buyer navigation. Reject missing parents and assignments that create a cycle. | Rename a parent and move a child. Both views show the new path and existing listings keep their category. Attempt to move a parent under its descendant and verify the tree stays intact. |
| SPEC-05 | REQ-05 · RSK-03, RSK-04, RSK-05 | Publish a shop-owned listing after validating its name, description, photos, category, price, and nonnegative whole-unit stock. Let its seller edit those fields or withdraw the listing while retaining its identity for existing orders. | Publish and edit a listing as its seller. Reject negative stock and an unknown category. Change stock to zero and verify that checkout can no longer sell a unit. |
| SPEC-06 | REQ-06 · RSK-04, RSK-17 | Browse the category tree or search published listings by name. Apply the selected category scope and all supplied filters together. Read province from the seller's shop and brand from the listing. | With matching names in two categories, search globally and within one category. Combine price, brand, and province filters and check the exact matching items. A listing with no brand cannot match a named brand. Verify ordering and fallback with the search-ranking checks below. |
| SPEC-07 | REQ-07 · RSK-04, RSK-05, RSK-08 | Load listing photos, seller, price, and availability from the current catalog record. Distinguish an active listing with zero stock from a purchasable listing. Enforce withdrawal when accepting purchases, including from previously opened pages. | Open an available listing, then withdraw it in the seller dashboard. Attempt checkout from the old page. No order is created. |

**Search ranking (SPEC-06).** First retrieve candidates matching the query and selected filters. The rule-based baseline ranks exact name matches first, followed by matches in the name or structured attributes, then description-only matches. Break ties by popularity and then listing ID. Let the ML ranker reorder the same candidates. On failure or timeout, return the baseline ordering for that query. For an unmatched query, return an empty result.

**Search acceptance.** For “wireless headphones”, verify an exact-name match precedes a description-only match in the baseline. Force an ML timeout and verify the same filtered baseline order returns. Evaluate both rankers on the same held-out shopper queries with graded relevance labels. Report NDCG@5 for each ranker and the difference. This measures whether more relevant products appear nearer the top. Record the measured result even if the baseline wins.

### Recommendations and privacy

| SPEC | Requirement and risks | Software behavior | Acceptance check |
| --- | --- | --- | --- |
| SPEC-08 | REQ-08 · RSK-06 | For home suggestions, rank candidates using permitted preferences or activity. For similar products, rank by shared catalog attributes and exclude the viewed listing. Maintain a precomputed popularity ranking that can be read independently of the model. Use it for new shoppers, model errors, and expiry of the configured ranking timeout. | With known catalog fixtures, inspect a home recommendation and a similar-products result. Use a new account, then force an error and a timeout separately. Each fallback returns eligible popular items when available. |
| SPEC-09 | REQ-09 · RSK-06 | Apply one eligibility filter to all recommendation lists immediately before returning them. Require an active listing, positive stock, and a current unit price less than or equal to any supplied per-item cap in the marketplace currency. Return a short or empty list when necessary. | Given a cap of 100, include an otherwise eligible item at 100 and exclude items at 101, with zero stock, or withdrawn. Repeat on the fallback path and with no qualifying items. |
| SPEC-10 | REQ-10 · RSK-07 | Display the tracking notice and save the preference on the account. After opt-out takes effect, check it before recording personalization events and before reading history or serving previously personalized suggestions. Continue serving popular products and processing purchases. | Opt out on device A. Browse and purchase on device B with the same account. Verify the purchase exists, no new personalization event was stored, and the recommendation path used no personal history or cached personal list. |

### Cart, checkout, and fulfillment

| SPEC | Requirement and risks | Software behavior | Acceptance check |
| --- | --- | --- | --- |
| SPEC-11 | REQ-11 · RSK-08 | Store cart lines by buyer and listing. Support adding, changing a positive whole-unit quantity, and removing a line. Group lines by their listing's shop and calculate displayed amounts from current unit prices. | Add items from two shops, change one quantity, and remove another line. Reopen the cart and verify its groups, quantities, and amounts against the current listings. |
| SPEC-12 | REQ-12 · RSK-08 | At confirmation, compare the reviewed quantities and prices with the cart and current listings, and recheck availability. If a price changed, return the revised figures and require a fresh confirmation. Apply the same checks when the buyer confirms again. | Change a price between review and confirmation. The first attempt shows the new price and creates no purchase. Confirm again with sufficient stock and verify the new amount. |
| SPEC-13 | REQ-13 · RSK-09 | Within one database transaction, validate current prices, condition each stock deduction on sufficient remaining stock and an active listing, create one order per shop, and record the simulated payment and allocations. Roll back all changes if any line or write fails. | Race two purchases for the last unit. Exactly one succeeds and stock ends at zero. In a separate two-shop checkout, force a failure after the first deduction. Verify original stock and zero new orders, allocations, or payments. |
| SPEC-14 | REQ-14 · RSK-09, RSK-10 | Assign each confirmation a key scoped to its buyer. Persist the key, confirmed contents, and purchase result in the checkout transaction with a uniqueness constraint. Reuse the committed result for identical retries and reject conflicting reuse. Compute each allocation from its shop order's lines using exact currency amounts and sum them for the simulated payment. | For shop totals of 60 and 40, submit the same confirmation concurrently and again after a lost response. Verify one purchase, two orders, one payment of 100, allocations of 60 and 40, and one set of deductions. A changed request with the same key produces no new purchase. |
| SPEC-15 | REQ-15 · RSK-11 | Copy the purchased listing name and confirmed unit price onto each order item at checkout. Read those saved values when displaying order history. | Rename, reprice, and then withdraw the listing. The order still displays the name and price on the original confirmation. |
| SPEC-16 | REQ-16 · RSK-03, RSK-12 | Show each shop its own incoming orders and line quantities. Record the seller's permitted fulfillment updates against the individual shop order. Read that same status in the buyer's purchase history. | Place a two-shop purchase. After one seller records dispatch, the buyer sees only that seller's order advance. The other seller cannot update it. |
| SPEC-17 | REQ-17 · RSK-12 | Check the selected order's current status against the agreed cancellation rule. In one transaction, transition an eligible order to canceled, restore its units, and reverse only its allocation. Serialize cancellation with dispatch. A repeated successful cancellation returns the canceled outcome without further adjustments. | Cancel one eligible order twice. Verify one restoration and one reversal, with its sibling order untouched. Reject cancellation of an ineligible order. Race dispatch against cancellation and verify that the recorded outcome and stock agree with the permitted transition order. |

## V2 — Deferred features

| SPEC | Requirement and risks | Software behavior | Acceptance check |
| --- | --- | --- | --- |
| SPEC-18 | REQ-18 · RSK-13 | Use a language-model API to interpret chat requests. Extract shopping constraints from chat and ask for clarification when ambiguity affects the result. Submit the clarified request to the V1 recommendation engine. Build links from returned listing IDs and support each product claim with catalog details. Report an empty match when no eligible listing satisfies the constraints. | Give the assistant an ambiguous budget, then clarify a per-item cap. Verify every link, price, and claimed feature against the eligible catalog. Ask for a feature absent from all listings and verify the response claims no confirmed match. |
| SPEC-19 | REQ-19 · RSK-14 | Authorize review creation against the buyer, order item, and agreed completion status. Enforce one submission per order item across retries and simultaneous requests. Let the purchaser edit or remove it. Retain submission identity after removal to enforce the once-per-item rule. | Reject a different buyer and an incomplete order. Submit twice concurrently for a completed item and verify one review. Let its author edit and remove it, then verify another user cannot edit it and the item cannot receive a second submission. |
| SPEC-20 | REQ-20 · RSK-15 | Display published reviews and compute their arithmetic mean per product. Use the same published ratings for product display and rating filters. Represent zero published ratings as unrated and apply the agreed search policy for that case. | Publish ratings of 3 and 5 and verify a mean of 4. Edit 3 to 5 and verify both display and filtering use 5. Remove both and verify the unrated state and the agreed filter behavior. |
| SPEC-21 | REQ-21 · RSK-15, RSK-16 | Resolve each review report to its review and product. Present both to the admin. Retaining the review preserves its current publication state. Removal excludes it from public reviews and the rating calculation. | Moderate one of two reviews for the same product. Verify that retaining it preserves both reviews and removing it changes the aggregate using only the remaining review. |
| SPEC-22 | REQ-22 · RSK-16 | Resolve each listing flag to the exact shop listing. Let an admin retain it or invoke the same withdrawal behavior used for seller withdrawal. Keep saved order items intact. | Flag one of two shops' listings for the same product. Retain it, then withdraw it. Check that only the withdrawn listing becomes unavailable at checkout and both shops' past orders keep their purchased details. |

Retrieval-augmented generation (RAG) over product descriptions or manuals is an optional extension to SPEC-18. Current price and stock come from the catalog when the assistant recommends a listing.
